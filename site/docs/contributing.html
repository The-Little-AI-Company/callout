Contributing.

Callout is small on purpose, and most of what makes it good lives in three YAML files rather than in code. You can improve a question, a label, or a joke without writing a line of TypeScript. The repository is at github.com/The-Little-AI-Company/callout.

Ground rules

  • The honesty rules are not negotiable. No verdict without a shown source. Sourced red needs a contradicting source or a fabricated quote. Helper calls are always labelled. Unsure names its reason. Confidence in words. No jokes in verdict copy. A pull request that bends any of these is closed, however clever.
  • Code owns the flow. Models judge. Jev answers narrow typed questions. The helper extracts, transcribes, drafts, and gives a labelled opinion. Thresholds and question wording live in the content file, never inline.
  • Nothing leaves the machine except calls to the three user-configured services and the pages fetched for evidence. No analytics, telemetry, accounts, or servers. Ever.
  • Attribution. MIT, copyright Jeff Kazzee. The notice stays. See License.

Where things are

PathWhat
content/questions.yamlEvery Jev question, reader label, threshold, verdict string, and meter level. The most valuable file to improve.
content/lines.yamlThe joke bank, tagged by surface. Never used in verdicts.
content/helper-prompts.yamlHelper prompts: extract claims, write queries, explain, judge, transcribe, answer.
engine/Pure TypeScript. Fast lane, deep lane, Jev client, helper adapter, page and video fetching. No Tauri, no DOM.
src/The popover, settings, and screenshot overlay. Plain TypeScript with Vite. No UI framework.
src-tauri/The Rust shell: tray, hotkey, clipboard capture, credential store, screen grab, windows.
site/This site. Static HTML and CSS, deployed by GitHub Pages.
test/Vitest suites, the twenty-sample evaluation set, and the eval runner.
docs/The PRD, the technical plan, decisions with reasons, the asset list, setup, costs.

Running it

npm install
npm test            # engine and site tests; a live DeepSeek test runs if DEEPSEEK_API_KEY is set
npm run typecheck
npm run dev         # popover in a browser at http://localhost:1420 (no hotkey, no secrets)
npm run tauri dev   # the real app on Windows; needs Rust and the WebView2 runtime

Copy .env.example to .env for keys used by tests and the eval script. The app itself never reads that file; users paste keys into Settings.

The Rust shell can be type-checked from Linux or Mac for the Windows target:

rustup target add x86_64-pc-windows-gnu
cd src-tauri && cargo check --target x86_64-pc-windows-gnu

The real Windows build runs in CI on every push. Download the installer from the workflow run's artifacts to test a branch on a Windows machine.

Evaluating changes

npm run eval:samples

Runs the fast lane and the deep lane over test/samples/samples.json with real keys and writes a review sheet (every verdict with its link, for a human to mark right or wrong) and a cost table (tokens by lane and step). Attach both to any pull request that touches content/. When you find a text the app gets wrong, add it to the samples with what you expected.

The product promise is precision on green and red, not coverage. A change that turns gray rows green at the cost of a wrong green is a regression even if it looks more impressive.

Changing content

A question, label, or threshold

  1. Edit content/questions.yaml. Every technique has a reader label, a textbook name, an instruction, and true and false criteria with examples. Keep labels plain: "Makes you feel you must act now", not "urgency appeal".
  2. Run the tests. The content test checks that ids are unique, all seven families are present, and verdict copy contains no jokes.
  3. Run the eval and look at what moved.

A joke line

Edit content/lines.yaml under the surface it belongs to. Aim at the text being checked, at manipulation techniques, or at the mascot. Never at the reader. Never imply a verdict. Keep it under about sixty characters.

A helper prompt

Edit content/helper-prompts.yaml. Prompts must keep the "do not add facts not in the passages" rules; Jev checks the output anyway, but a prompt that invites invention wastes calls and drops sentences.

Pull requests

  • One build-order step or less per PR. Small and reviewable.
  • Say what you tested on Windows and what you did not.
  • CI must be green: tests, type check, and the Windows build.
  • No new dependencies without a sentence on why. The app is meant to idle small in the tray.
  • Match the existing voice: dry, plain, no exclamation marks in anything a reader sees as a finding.
  • Record a real design choice in docs/DECISIONS.md with its reasoning, the way the existing entries do.

Releases

Maintainers bump the version in package.json, src-tauri/tauri.conf.json, and src-tauri/Cargo.toml, then tag vX.Y.Z on main. CI builds, then publishes a GitHub Release with Callout-Setup.exe and Callout.msi. The site's download button follows the latest release on its own.

Reporting problems

Open an issue with the build number from Settings, what you highlighted (or that you would rather not say), what the popover showed, and what you expected. Settings has a Copy feedback report button that gathers the build, settings, and usage counts without any checked text unless you tick the box.
